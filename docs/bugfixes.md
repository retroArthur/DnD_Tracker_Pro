## Muster / Lessons Learned

| Muster                                                                         | Vermeidung                                                                                                    |
| ------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------- |
| `saveUndoState()` fehlt bei Delete/Edit                                        | Bei jeder Lösch-/Bearbeitungsfunktion prüfen                                                                  |
| CSS-Klassen im HTML ohne Definition                                            | HTML + CSS immer zusammen implementieren                                                                      |
| Selbstbezüge in hierarchischen Daten                                           | Filter auf `parentId !== id` prüfen                                                                           |
| `document.execCommand()` deprecated (abgelöst, Phase 9 — 0 Aufrufe im Quellbaum, Stand 2026-10-14) | Neue Editor-Funktionen über die Selection/Range-Helfer in `ui/editors/rich-text.js`; `execCommand` nicht wiederbeleben (`DOC-12` hält die Zahl) |
| Dropdowns nur bei Init gefüllt                                                 | Beim Öffnen des Formulars Selects neu populieren                                                              |
| Kategorie-übergreifende Parent-Refs                                            | Prüfen ob Parent in gleicher Kategorie ist, sonst als Root behandeln                                          |
| `setInterval` ohne Cleanup                                                     | Immer prüfen ob Interval existiert und clearInterval vor neuem Start                                          |
| Magic Numbers                                                                  | Konstanten mit sprechenden Namen verwenden                                                                    |
| `window[...]` dynamische Aufrufe                                               | Whitelist für erlaubte Funktionsnamen verwenden                                                               |
| Fehlende Accessibility                                                         | ARIA-Attribute für dynamische UI-Elemente (Toast, Dialoge)                                                    |
| ID-Vergleich String vs Number                                                  | Immer `parseEntityId()` verwenden                                                                             |
| innerHTML mit Template-Literalen                                               | textContent für unsicheren Content, DOM programmatisch erstellen                                              |
| Direktes Zuweisen von parsed JSON                                              | Deep Clone + Schema-Validierung vor Zuweisung                                                                 |
| Service Worker ohne Caching                                                    | Cache-First, nur im eigenen Cache-Namensraum (App + Scope, R08)                                               |
| `??` Operator fängt NaN nicht                                                  | Explizite NaN-Prüfung mit `!isNaN(value)` zusätzlich verwenden                                                |
| Button für nicht-existente View                                                | Vor Feature-Buttons prüfen ob View/Handler existiert                                                          |
| querySelectorAll in Schleifen                                                  | Statische NodeList - Array.from() nutzen bei remove()                                                         |
| Content ohne sanitizeHTML()                                                    | Immer sanitizeHTML() für User-Content wie description, content                                                |
| HTML maxlength != JS Validierung                                               | Serverseitig/JS-seitig immer auch validieren, nicht auf HTML vertrauen                                        |
| User-Input ohne Escape in Icon-Feldern                                         | Auch "sichere" Felder wie Icons mit esc() escapen                                                             |
| Unbegrenzte Schleifen bei User-Input                                           | Immer maxValue/maxIterations setzen (DoS-Schutz)                                                              |

### IndexedDB-Save meldete Erfolg vor dem Transaktions-Commit (R04, U3)

- **Problem:** `saveToIndexedDBFallback()` löste bei `request.onsuccess` auf. Brach der Commit danach ab (Quota, E/A-Fehler), hatte `saveImmediate()`/`save()` im >5-MB-Zweig die localStorage-Kopie samt `_ts` schon entfernt und „Gespeichert“ gemeldet — der nächste Start lud eine **leere** Kampagne. Zusätzlich prüfte das Entfernen der LS-Kopie nach einem `await` nicht, ob inzwischen ein neuerer Save localStorage geschrieben hatte (Überhol-Rennen), und ein später Retry eines älteren Stands konnte nach dem Fix einen neueren IDB-Stand überschreiben.

Toter `saveToIndexedDB()` in `core/init.js` entfernt.
- **Regel:** Schreibende IDB-Transaktion nur über `idbWriteTx()` bestätigen; `request.onsuccess` ist keine Bestätigung; Commit-Fehler kommen nur als `abort`; LS-Kopie erst nach Commit und nur ohne neueren LS-Write entfernen; überholte Retries verwerfen. Zwischen `++_persistGeneration` und dem localStorage-Write nie ein `await`. Einzige Ausnahme vom Wächter: `statsIdbPut()` (fire-and-forget).

### IndexedDB-Double plante Transaktionen falsch und verdeckte damit echte Rennen (F1, Testinfrastruktur)

- **Problem:** `tests/unit/helpers/fake-idb.js` — die gemeinsame Werkbank von `conflict-reload`, `unload-persistence` und `idb-transaction-commit` — verkettete **nur** readwrite-Transaktionen (`rwKette`). Eine readonly-Transaktion startete sofort bei der Erstellung, ohne auf frühere, noch offene readwrite-Transaktionen zu warten, und ein gehaltener Lese-Request (Politik `halten()`) nahm seinen Schnappschuss bei der **Erstellung**. Folge: ein Schreibvorgang, der während eines gehaltenen Lesens erstellt wurde, schrieb sofort fest — im Browser unmöglich. Genau dieses Muster ist das R06-Rennen (eigener `saveImmediate()` im Ladefenster des Konflikt-Neuladens): das Double zeigte es als in Ordnung, obwohl IndexedDB danach den verdrängten Stand trug und `D` den geladenen. Umgekehrt las eine readonly-Transaktion, die nach einem noch offenen readwrite erstellt wurde, den Stand **vor** dessen Commit.
- **Ursache:** Die Serialisierung war als „readwrite nicht parallel zueinander“ gedacht, nicht als die Planungsregel von IndexedDB. Der Schnappschuss war der Behelf, mit dem die fehlende Wartebeziehung für gehaltene Lesevorgänge kaschiert wurde.
- **Fix:** Eine Liste **aller** Transaktionen in Erstellungsreihenfolge (`alleTx`, je Eintrag `{ id, mode, erledigt, fertig }`). Bei der Erstellung werden die Blocker nach IndexedDB 3.0 (§transaction scheduling) bestimmt: readwrite wartet auf alle früher erstellten, noch nicht beendeten Transaktionen, readonly nur auf die früher erstellten readwrite; readonly untereinander laufen nebenläufig. Gestartet wird über `Promise.all(blocker.map(b => b.fertig)).then(() => naechsterTask(starten))`. `fertig` löst dort auf, wo vorher nur die readwrite-Kette freigegeben wurde — jetzt für **jeden** Modus und auf beiden Wegen, `commit()` und `abbrechen()`, damit eine abgebrochene Transaktion ihre Nachfolger nicht dauerhaft blockiert. Der Erstellungs-Schnappschuss in `neuerRequest()` ist entfallen: später erstellte Schreibvorgänge warten ohnehin hinter dem gehaltenen Lesen. Die `halten()`-Schnittstelle ist unverändert. Ein Schnappschuss, der eine fehlende Wartebeziehung ersetzt, macht das Double in genau dem Fall blind, für den es gebaut wurde. ### nextId() und normalizeEntityIds() vergaben an der ID-Obergrenze doppelte, ungültige IDs (F6)

- **Problem:** Trägt eine Sammlung eine ID von genau `ENTITY_ID_MAX` (1e15), lieferte `nextId(type)` bei **jedem** Aufruf dieselbe Zahl 1e15 + 1 — ungültig und beliebig oft doppelt. `normalizeEntityIds()` vergab aus demselben Grund die ungültigen IDs 1e15 + 1 und 1e15 + 2, die `validateDataIntegrity()` bei jedem Laden erneut umnummerierte. **Zweite Runde (Korrekturrunde F6):** dieselbe Fehlerklasse trat eine Ganzzahl _unterhalb_ der Obergrenze erneut auf. Bei `max(ID) == 1e15 − 1` ist die Untergrenze 1e15 noch gültig und wird ausgegeben — der Zähler springt dabei auf das ungültige 1e15 + 1. Der nächste Aufruf verwarf ihn und gab dieselbe 1e15 erneut aus: drei Stapelaufrufe ohne `push` dazwischen lieferten dreimal 1e15. Doppelte IDs sind die R03-Fehlerklasse: `D.entities.filter(e => e.id !== id)` löscht dann mehrere Entitäten auf einmal (gemessen: ein Löschen entfernte drei Entitäten). **Dritte Runde (Korrekturrunde F6, Runde 2):** die zweite Korrektur hatte nur die Grenze um eine Ganzzahl verschoben, nicht die Fehlerklasse behoben. Allgemein gemessen: bei `max(ID) == 1e15 − k` waren ab dem (k+1)-ten Aufruf eines Stapels die IDs zyklisch doppelt — `k = 2` ergab `[1e15−1, 1, 1e15−1, 1, …]`, also zwei verschiedene IDs von acht; über den echten Schreibpfad (Merge-Zweig des Imports, 10 NSCs) blieben zwei verschiedene von zehn, und **ein** Löschen entfernte fünf Einträge.
- **Ursache:** Beide Stellen rechnen mit der Untergrenze `max(gültige ID) + 1`. An der Obergrenze ist diese Untergrenze selbst **keine** gültige ID mehr (`isValidEntityId(1e15 + 1) === false`), also zählt `maxEntityId()` sie nicht mit und der Zähler wird als ungültig verworfen — die Untergrenze blieb damit dauerhaft auf demselben ungültigen Wert stehen. Eine Ganzzahl darunter liegt die Ursache nicht in der Untergrenze, sondern im **Zähler**: er ist die einzige Erinnerung daran, dass eine ID im laufenden Stapel schon vergeben wurde (die Sammlung weiß es erst nach dem `push`). Wird er ungültig, ist diese Erinnerung verloren und der Generator fällt auf die noch gültige Untergrenze zurück. Kein App-Schreibpfad erzeugt solche IDs (`nextId` oder `Date.now()` ≈ 1,8e12); eine fremde oder beschädigte Datei mit einer ID nahe 1e15 nimmt der Normalisierer aber ausdrücklich an — genau das R03-Bedrohungsmodell. Der Stapelpfad ist erreichbar und nicht hypothetisch: `systems/spellslots/import-export.js` ruft im Merge-Zweig `items.map(item => ({ ...item, id: nextId(type) }))` auf und schreibt erst **danach** per `ioSetArray` in `D[type]`. Die dritte Runde zeigte, dass nicht der _Wert_ des Zählers die Ursache war, sondern der **Speicherort** der Erinnerung: der Sättigungszweig schrieb die niedrige Lücken-ID in den persistenten Zähler. Dort liegt sie unter der Untergrenze `max(ID) + 1`, gilt beim nächsten Aufruf als veraltet und wird verworfen — womit die Untergrenze erneut vergeben wurde. Ein Zähler, dessen Wertebereich die Vergabe nicht abbilden kann, taugt nicht als deren Gedächtnis.
- **Fix:** Modulinterner Helfer `nextFreeEntityId(items, start)` in `utils/utilities.js`: sammelt die belegten gültigen IDs, startet beim übergebenen Kandidaten (nicht vergebbar → 1) und sucht aufwärts die erste Lücke. Dazu das Prädikat `isMintableEntityId(n)` = gültig **und** `n < ENTITY_ID_MAX`: neu gemünzt wird nur, was `id + 1` noch als gültigen Zähler zulässt. `nextId()` greift auf die Lückensuche zurück, sobald die berechnete ID nicht vergebbar ist (ungültig **oder** genau `ENTITY_ID_MAX`), und schreibt weiter `_nextId[type] = id + 1`. `ENTITY_ID_MAX` bleibt als _gespeicherte_ ID gültig (fremde Dateien), wird aber nie neu vergeben — das kostet genau eine von 1e15 IDs und hält im Gegenzug die Invariante: der Zähler ist nach **jedem** `nextId()` selbst eine gültige ID und kann also nicht verworfen werden. **Korrektur der dritten Runde:** die Stapel-Erinnerung liegt nicht mehr im Zähler, sondern in `SATURATION_CURSOR` — einer modulinternen `Map` je Typ, die bewusst **nie** persistiert wird und den Suchzeiger der Lückensuche innerhalb eines Stapels trägt. Der persistente Zähler bekommt in der Sättigung `ENTITY_ID_MAX` selbst: eine gültige ID (wird nie verworfen), die nie neu gemünzt wird — also das dauerhafte Signal „gesättigt“, das jeden weiteren Aufruf in die Lückensuche schickt. Ein Typ unterhalb der Sättigung räumt seinen Zeigereintrag selbst wieder ab. Nach einem Neuladen ist der Zeiger weg, die vergebenen IDs stehen dann aber in der Sammlung, also setzt die Lückensuche dort korrekt fort. Damit liefern Stapelaufrufe ohne `push` dazwischen nie zweimal dieselbe ID — gemessen für `max(ID) = 1e15 − k`, `k = 0 … 6`, je acht Aufrufe. `normalizeEntityIds()` führt je Typ ein `taken`-Set aller gültigen IDs der Sammlung (auch der weiter hinten stehenden) und setzt bei ungültigem `next` auf 1 zurück, bevor es die erste freie Lücke sucht; dort liegt die Erinnerung vollständig im `taken`/`seen`-Set, also darf es 1e15 vergeben. Unterhalb der Sättigung ist das Verhalten unverändert: `next` startet über dem Maximum, also greift die Suchschleife nie und die Zähler bleiben monoton. **Korrektur der Abschlussrunde (G2, siehe unten):** dieser Zeiger heißt jetzt `MINT_CURSOR`, wird bei jedem Münzen fortgeschrieben, und `ENTITY_ID_MAX` im Zähler ist **kein** Sättigungssignal mehr — die Sättigung entscheidet allein die Sammlung.
- **Regel:** Wer eine Obergrenze prüft, muss auch den Fall behandeln, dass „Maximum + 1“ diese Grenze überschreitet — **und** den Nachbarfall, in dem erst der _fortgeschriebene_ Zustand die Grenze überschreitet. Trägt ein Zähler die Vergabe-Erinnerung, darf er nie in einen Wert laufen, den die eigene Gültigkeitsprüfung anschließend wegwirft: der Generator liefert sonst stillschweigend Duplikate statt zu scheitern. Und: eine Invariante, die eine Einheit im Quellkommentar behauptet, muss auch für den Nachbarwert der Grenze geprüft sein — sonst behauptet die Dokumentation eine Sicherheit, die es nicht gibt. Die dritte Runde schärft das: wer nur den _gemeldeten Wert_ heilt, verschiebt die Grenze statt die Fehlerklasse zu schließen. Ein Grenzfall gehört als **Matrix** über die Nachbarwerte geprüft (hier `k = 0 … 6`), nicht als Einzelfall. Und Zustand, der in einem persistenten Feld nicht darstellbar ist, gehört nicht in dieses Feld: entweder in eine eigene, bewusst flüchtige Struktur — oder das Feld muss einen Wert tragen, den die eigene Gültigkeitsprüfung überlebt.
- **Bekannte Grenzen:** `normalizeEntityIds()` nummeriert weiter um, ohne Verweise (`giverId`, `relations.targetId`, …) mitzuziehen (U2 open:3, eigenes Vorhaben). In der Sättigung sind die Zähler nicht mehr monoton: gelöschte IDs werden dort bewusst wiederverwendet, weil es oberhalb keine gültige ID mehr gibt. `nextFreeEntityId()` wirft `Error('Keine freie ID')`, wenn jede ID von 1 bis 1e15 − 1 belegt wäre — praktisch unerreichbar (1e15 Einträge), aber bewusst ein sichtbarer Fehler statt einer ungültigen oder doppelten ID.

- **Tests:** `tests/unit/next-id.test.js` (N9: Stapelvergabe an der Obergrenze liefert gültige, eindeutige IDs, plus `isValidEntityId(5e15) === false` als Pin für die Obergrenze selbst; N10: `normalizeEntityIds` an der Obergrenze; N11: Stapelvergabe bei `max(ID) == 1e15 − 1` samt „ein Löschen entfernt genau eine Entität“; N12: der gespeicherte Zähler ist nach jedem `nextId()` selbst eine gültige ID — für `max(ID)` = 1e15 − 2, 1e15 − 1 und 1e15; N13: die Sättigung als Matrix über `max(ID) = 1e15 − k`, `k = 0 … 6` — acht Stapelaufrufe ohne `push` liefern acht verschiedene, gültige IDs, der Zähler bleibt in jedem Schritt gültig und ein Löschen entfernt danach genau eine Entität; N14: der Datei-Rundlauf — der nur im Speicher geführte Zeiger darf nach einem Neuladen nicht mit gespeicherten IDs kollidieren); `tests/unit/campaign-schema.test.js` (S14 pinnt Schritt 7 `ensureCampaignContainerLists()` — ohne ihn bleiben `calendar.events`, `initiative.combatants` und `soundboard.scenes` `null`, und Verbraucher wie `features/initiative.js` greifen ungeschützt darauf zu)

### Der Cache-Bump-Wächter in build.py fiel offen aus, wenn stdout seine Meldung nicht kodieren konnte (F7)

- **Problem:** `bump_sw_cache_version()` (R08) soll einen Production-Build abbrechen, wenn der `CACHE_VERSION`-Platzhalter in `sw.js` nicht genau einmal vorkommt — sonst liefert der Cache-First-Service-Worker nach dem Deploy weiter die alte App aus. Der Wächter druckte seine `[ABORTED]`-Meldung mit einem rohen `print()` **vor** `sys.exit(1)`, und die Meldung enthielt einen Gedankenstrich (U+2014). Auf einer Konsole mit cp850, cp437 oder einer ascii-Umleitung wirft dieses `print()` `UnicodeEncodeError`, **bevor** `sys.exit(1)` läuft. Die Aufrufstelle in `build()` fing das mit `except Exception as e: log.warning(...)`: der Build lief weiter und schrieb `dist/dnd-tracker-optimized.html` — mit veraltetem oder fehlendem `dist/sw.js`, also genau dem stillen Nicht-Bump, den der Wächter ausschließen soll. Gemessen: cp1252 und utf-8 ergeben `SystemExit(1)`, cp850/cp437/ascii ergeben `UnicodeEncodeError`; über den echten `build(production=True)` kehrte der Build unter cp437 normal zurück, mit nur einer Warnzeile. Zweiter Befund, rein testseitig: nichts pinnte die **Schreib**seite des Laufzeit-Caches in `sw.js`. Die Leseseite war über S7/S8/S9a und den Quelltext-Wächter gebunden, aber ein entferntes `cache.put()` und ein `put()` in einen zusätzlichen, nicht namensräumigen Cache (`caches.open(CACHE_VERSION)`) ließen die Suite beide 18/18 grün.

Dazu ein `except Exception`, das als „Kopieren ging nicht“ gedacht war, aber jede Ursache gleich behandelte. Der Kommentar darüber begründete nur, warum `SystemExit` durchkommt — nicht, warum eine gewöhnliche Exception verschluckt werden darf.
- **Fix:** Die `[ABORTED]`-Meldung ist rein ASCII (` - ` statt `—`); der Docstring sagt, warum das eine Zusicherung ist und keine Kosmetik. Die Schreibseite pinnt jetzt `S7b`.
- **Regel:** Ein Wächter darf seinen Abbruch nie hinter eine Ausgabe stellen, die scheitern kann: erst `sys.exit()`/`raise`, dann melden — oder die Meldung muss in jedem Codec darstellbar sein. Fehlermeldungen in `build.py` deshalb rein ASCII halten (`log.*` fängt `UnicodeEncodeError` ab und ersetzt Zeichen, ein rohes `print()` nicht). Und: `except Exception` um einen Block, der einen Wächter aufruft, macht den Wächter wirkungslos — der Fangbereich muss so eng sein wie der Fehler, der wirklich gemeint ist (hier `OSError`). Test-Gegenstück: pinnt eine Suite nur die Leseseite eines Caches, überlebt jede Mutation der Schreibseite — beide Richtungen gehören gebunden.

Sie stehen aber außerhalb jedes `try`, scheitern also laut statt still, und wurden nicht angetastet. `dist/sw.js` entsteht nach wie vor nur im Production-Build; ein Dev-Build lässt eine veraltete Kopie stehen (unverändert aus R08).

### R02/R04 Nachtrag: Persistenz-Schreibpfade — überholte Wiederholungen, Entladen-Writes, Aufräumen unter der Sperre, Rückfrage ohne Baseline, automatische Saves (F2)

- **Problem:** Fünf Befunde derselben Familie, alle an den Schreibpfaden von `systems/spellslots/persistence.js`.
  **(A)** Der **innere** `catch (idbError)` beider Save-Pfade (`saveImmediate`, `_persistNow`) rief `_reportPersistFailure()` bedingungslos — auch dann, wenn ein neuerer Save längst lief und persistierte. Folge: lauter Toast „❌ Speichern fehlgeschlagen … JETZT exportieren!“, ein Notfall-Export (~5 MB Download) und eine Anzeige, die auf `error` **endet**, obwohl der Stand sicher lag; dazu blieb `_persistFailureStreak` gesetzt, sodass der nächste **echte** Fehlschlag keinen Export mehr bekam. Der Überholschutz war nur am **äußeren** `catch` gesetzt (A1b pinnte genau diesen).
  **(B)** Der >5-MB-Zweig von `persistOnUnload` stieß `_persistNow(false)` für **jede** Änderung an, auch für harmlose Nebenänderungen ohne `save()` (Würfelhistorie). Sein `put` wird **nach** dem laufenden ausdrücklichen Save eines anderen Tabs angelegt und committet danach — der andere Tab verlor seine Arbeit ohne Rückfrage. Der localStorage-Fehler-Rückfall am Ende derselben Funktion tat dasselbe.
  **(C)** Der Nachlauf nach einem bestätigten IndexedDB-Commit (`if (_lsWriteGeneration < generation) { remove(key); remove(key + '_ts') }`, vier Stellen) und `_onPersistSuccess()` ignorierten `_campaignWritesRetired`. Der Umzugs-Assistent schreibt den Import über `importFullExport` (reines `StorageAPI`, ohne Generationszähler) und sperrt **danach** die Schreibpfade — ein noch laufender IndexedDB-Save dieses Tabs löschte danach den frisch importierten Schlüssel samt `_ts`, und der nächste Start lud die alte IndexedDB-Kopie, obwohl der Assistent Erfolg gemeldet hatte. `await retireCampaignWrites()` **vor** dem Import hilft nicht: `saveToIndexedDBFallback` gibt die Settle-Warter im `finally` frei, also **vor** dem Nachlauf des Aufrufers.
  **(D)** `persistOnUnload` kehrte an der Baseline-Prüfung zurück, **bevor** `explicit` berechnet war. Ein Tab, dessen `load()` still gescheitert ist, verwarf beim Schließen einen ausstehenden ausdrücklichen Save ohne die D5-Rückfrage — der Rohtext blieb erhalten, die letzte Eingabe des Nutzers verfiel stumm.
  **(E)** `saveAutomatic()` prüfte die Veraltung **nur beim Aufruf**. Der Timer-Körper der 300-ms-Entprellung prüfte nie erneut, und `persistOnUnload` zählte jeden ausstehenden Timer als ausdrücklich. Gemessener Ablauf: t=0 speichert B ausdrücklich (fällig t=300); t=100 ruft der frische Tab A `saveAutomatic()` (fällig t=400); t=300 schreibt B, A ist ab jetzt veraltet; t=400 schreibt A trotzdem und macht Bs Arbeit zunichte. B schließt danach ohne Rückfrage, seine Änderung ist weg. Zweiter Fall: ein veralteter Tab, dessen einziger ausstehender Save automatisch ist, forderte beim Schließen die Rückfrage an — D5 beschränkt sie auf ausdrückliche Saves.
- **Ursache:** (A) Der Überholschutz war als Eigenschaft **eines** `catch` gedacht statt als Eigenschaft des **Save-Aufrufs**: jeder Ausgang, der ein Ergebnis meldet, braucht ihn. (B) `explicit` wurde berechnet, aber nur für die Rückfrage benutzt, nicht für die Entscheidung, **ob** geschrieben wird. (C) `_campaignWritesRetired` sperrte die **Anfänge** der Schreibpfade, nicht ihre **Nachläufe**; ein Save, der vor der Sperre gestartet ist, lief mit seinen alten Annahmen weiter. (D) Eine frühe Rückgabe ohne Nebenwirkung wurde vor die Berechnung gestellt, die für ihre Vollständigkeit nötig ist. (E) Eine Prüfung „zum Zeitpunkt des Einplanens“ galt als Prüfung „zum Zeitpunkt des Schreibens“ — eine Zeitfenster-Verwechslung (TOCTOU) über die gesamte Entprellungsdauer.
- **Fix:**
  (A) Als **erste** Anweisung beider inneren `catch (idbError)`: `if (generation !== _persistGeneration)` → `saveImmediate` liefert `{success:false, superseded:true, error:'superseded'}`, `_persistNow` kehrt zurück. Vor jedem Log und jedem `_reportPersistFailure()`. Belastbar, weil gesperrte und schlüssellose Saves vor `++_persistGeneration` zurückkehren: eine neuere Generation ist immer ein echter Save, der sein Ergebnis selbst meldet.
  (B) Der >5-MB-Zweig beginnt mit `if (!explicit) …` und schreibt nur für ausdrückliche Arbeit; der localStorage-Fehler-Rückfall lief zunächst ebenso nur `if (explicit)` — **beides war unvollständig, siehe den Nachtrag „Runde 2“ direkt unter diesem Eintrag**.
  (C) `_onPersistSuccess()` beginnt mit `if (_campaignWritesRetired) { _retiredPersistSkipped = true; return; }`; die vier Nachlauf-Wächter lauten `if (_lsWriteGeneration < generation && !_campaignWritesRetired)` und setzen `_retiredPersistSkipped = true`, wenn sie **nur** wegen der Sperre übersprungen wurden. `resumeCampaignWrites()` holt diesen übersprungenen Nachlauf mit einem `save()` nach — sonst bliebe nach einem abgebrochenen Löschen oder Leeren eine **ältere** localStorage-Kopie **mit** `_ts` liegen, die `load()` bevorzugt.
  (D) Die Baseline-Prüfung lautet `if (!key || !b || b.key !== key) { if (key && explicit) _askToStay(event); return; }` — sie schreibt nie, sie fragt nur.
  (E) Neues Modul-Flag `_pendingSaveAutomaticOnly`: `save()` löscht es (jeder Aufruf über `save()` ist ausdrücklich), `saveAutomatic()` setzt es **nach** dem `save()` wieder, sofern nicht schon ein ausdrücklicher Save ausstand; `cancelPendingSave()` räumt es ab, `retireCampaignWrites()` merkt es sich für den verworfenen Save und `resumeCampaignWrites()` stellt es wieder her. Der Timer-Körper prüft die Veraltung **erneut** und stellt dann die Anzeige wieder her, die `save()` auf `saving` gesetzt hatte. `persistOnUnload` nutzt `_hasExplicitPendingWork()` statt `!!saveTimeout || …`: ein rein automatischer Timer zählt nicht mehr als ausdrückliche Arbeit.
  Neu exportiert für die Folgeeinheiten: `areCampaignWritesRetired()`, `getPersistGeneration()`, `waitForPersistSettle()`.
- **Regel:** Ein Überholschutz gehört an **jeden** Ausgang eines Save-Aufrufs, nicht an einen. — Ein Wert, der entscheidet, ob gewarnt wird, muss auch entscheiden, ob **geschrieben** wird: eine Änderung, um die niemand gebeten hat, darf einen anderen Tab nie überschreiben (D4). — Eine Schreibsperre muss die **Nachläufe** laufender Schreibvorgänge mitsperren, nicht nur neue Anfänge; und wer einen Nachlauf überspringt, muss ihn beim Aufheben der Sperre **nachholen**, sonst bleibt eine halbe Kopie zurück. — Eine frühe Rückgabe darf nie vor der Berechnung stehen, von der ihre Vollständigkeit abhängt. — Und: eine Prüfung beim Einplanen ist **keine** Prüfung beim Ausführen. Wer entprellt, prüft zweimal.
- **Bekannte Grenzen:** Ausdrückliche Saves in einem veralteten Tab bleiben last-writer-wins (D4): nach „Bleiben“ überschreibt der ausstehende Save weiter den anderen Tab, das Konflikt-Banner ist die einzige Warnung. Die Veraltung wird nach wie vor erst **nach** dem Commit signalisiert (`_rev` in `_onPersistSuccess`), also bleibt für `saveAutomatic()` ein kleines Fenster, in dem ein laufender fremder Save noch nicht sichtbar ist. Ob eine entladende Seite ihre IndexedDB-Transaktion überhaupt noch committet, garantiert kein Browser — die Werkbank lässt sie committen und prüft damit den strengeren Fall. `resumeCampaignWrites()` holt den übersprungenen Nachlauf über den entprellten `save()` nach, also erst 300 ms später; bis dahin liegen beide Kopien nebeneinander (die IndexedDB-Kopie ist die neuere, `load()` entscheidet über `_ts`). ### Runde 2 zu (B): der Entlade-Flush schrieb weiter, und die Notrettung „localStorage voll“ fiel aus (F2)

- **Problem:** Befund (B) war nur für den Fall geschlossen, den `U9f` nachstellt — `D` geändert, **kein** ausstehender Timer. Mit der gewöhnlichsten Zutat, einem ausstehenden Session-Timer-Autosave (`saveAutomatic()`), kam der `put` zurück, nun aus dem `pagehide`-Hörer über `flushPendingSave()` statt aus `persistOnUnload`: der lehnte korrekt ab, ließ den Timer aber stehen (richtig — nach „Bleiben“ muss er laufen), und die Entlade-Sequenz zog ihn danach doch vor. `flushPendingSave()` prüft nur `isCampaignStorageStale()`, und das sieht den committeten, aber noch nicht `_rev`-markierten Save eines anderen Tabs nicht. Gemessen: 2 `put`s, der andere Tab verlor seine Arbeit — und **stiller** als vorher, weil `_hasExplicitPendingWork()` den rein automatischen Timer aus der Rückfrage heraushält, die vorher noch kam.
  Zweiter Fall, ein einzelner Tab: Der letzte Zweig von `persistOnUnload` ist die Notrettung für den dokumentierten Fall „localStorage voll“ — der synchrone Write ist an der Quota gescheitert, `cancelPendingSave()` hat den Timer schon verworfen und `++_persistGeneration` ist gelaufen, es holt diesen Save also **nichts** nach. `if (explicit)` machte ihn von einem Flag abhängig, das mit dem Quota-Fehlschlag nichts zu tun hat: mit einem automatischen Timer wurde nirgends geschrieben und nichts gefragt — die Daten des Nutzers waren weg, ohne Hinweis. **Der hier gezogene Schluss „hier gibt es auch keinen Fremdschreiber zu schützen“ war falsch — siehe den Nachtrag „Runde 3“ direkt unter diesem Eintrag.**
- **Ursache:** Die Entscheidung „diesen Save nicht ausführen“ wurde in `persistOnUnload` getroffen, aber nirgends **festgehalten** — die weiteren Hörer derselben Entlade-Sequenz (`pagehide`, `visibilitychange` → hidden) wussten nichts davon und trafen sie neu, mit einem schwächeren Kriterium. Und ein Schutz gegen das Überschreiben **fremder** Arbeit wurde von einem Pfad entfernt, der für „hier gibt es nur noch eigene Arbeit zu retten“ gehalten wurde — eine Fehlannahme, siehe „Runde 3“.
- **Fix:** Neues Modul-Flag `_unloadFlushDeclined`: `persistOnUnload` setzt es als erste Anweisung (bis eine Schreibentscheidung fällt, gilt der Save als abgelehnt), `flushPendingSave()` kehrt dann zurück, und `save()` (neu eingeplant) sowie `cancelPendingSave()` (verworfen) heben es auf — läuft der Timer regulär, greift ohnehin die `saveTimeout`-Prüfung. Interne Festschreib-Stellen verlangen den Save ausdrücklich: `flushPendingSaveAndSettle()` ruft `flushPendingSave({ force: true })`. Der `pagehide`-Hörer ist als `() => flushPendingSave()` gebunden, damit das Ereignisobjekt nicht als Optionen durchschlägt. Im >5-MB-Zweig fragt der Tab jetzt nach, wenn er einen ausstehenden Save ablehnt (`if (saveTimeout) _askToStay(event)`) — geschrieben wird nicht (D4), entschieden wird vom Nutzer (D5); eine bloße Änderung ohne jeden ausstehenden Save fragt weiterhin nicht (`U9f`). Die Notrettung am Ende lief damit wieder **bedingungslos** (`_persistNow(false); _askToStay(event);`) — **das war die Fehlkorrektur, die „Runde 3“ zurücknimmt.**
- **Regel:** Wer beim Entladen entscheidet, **nicht** zu schreiben, muss diese Entscheidung für die restliche Entlade-Sequenz festhalten — `beforeunload` ist nicht der letzte Hörer, `pagehide` und `visibilitychange` folgen und würden sie sonst neu und schwächer treffen. — Und: verweigertes Schreiben darf nicht stilles Verwerfen heißen. Entweder es gibt einen anderen Weg (Rückfrage, späterer Timer) oder es wird geschrieben; ein Zweig, der die **letzte** Gelegenheit ist, darf nie an einem Flag hängen, das ein anderes Problem beschreibt.
- **Bekannte Grenzen:** Die Rückfrage zeigen Browser nur nach einer Nutzeraktivierung und ohne eigenen Text; verlässt der Nutzer die Seite trotzdem, verfällt die nicht ausdrückliche Änderung — bewusst, denn geschrieben wird sie nicht. Die Notrettung ist ein `put` ohne Zusage: ob eine entladende Seite ihre IndexedDB-Transaktion noch committet, garantiert kein Browser. Läuft dabei ausnahmsweise doch der Save eines anderen Tabs, bleibt das schmale Fenster vor dem `_rev`-Marker offen. ~~Im Quota-Fall deckt der BroadcastChannel es ab (`U9d`).~~ **Falsch:** `U9d` wartet Bs Save mit `await` ab (Broadcast zugestellt, A ist veraltet und schreibt gar nicht); das offene Fenster ist der **laufende** Save, also genau der Fall, für den `U9f`/`U9g` gebaut wurden. Siehe „Runde 3“.

### Runde 3 zu (B): die bedingungslose Notrettung überschrieb den laufenden Save eines anderen Tabs (F2)

- **Problem:** Runde 2 hat den `if (explicit)`-Wächter vor der Notrettung „localStorage voll“ entfernt, mit der Begründung, auf diesem Pfad gebe es keine fremde Arbeit zu schützen. Das trifft nicht zu. Gemessen an der echten Mehr-Tab-Werkbank, Kampagne **unter** 5 MB, localStorage voll, zwei Tabs: B fügt „Borin“ hinzu und ruft `saveImmediate()`; dessen synchroner localStorage-Write scheitert an derselben Quota und der Save läuft nach IndexedDB. A hat nur eine harmlose Nebenänderung (`D.diceHistory`, **kein** `save()`), gilt als frisch und schließt. Die Notrettung setzte dann einen zweiten `campaigns`-`put` ab, der **nach** Bs `put` angelegt wird und danach committet: Endstand `['Aria']`, nächster Start `['Aria']` — Bs bestätigte, ausdrückliche Arbeit war unwiederbringlich weg, ohne Warnung an B. Mit der gewöhnlichsten Zutat, einem ausstehenden Session-Timer-Autosave, genauso; `_unloadFlushDeclined` hilft hier nicht, weil `persistOnUnload` **selbst** schreibt. Und As Rückfrage kam **nach** `_persistNow(false)` — der `put` war schon abgesetzt, egal wie der Nutzer entscheidet, „der Nutzer entscheidet“ galt auf diesem Pfad also nicht.
- **Ursache:** Aus „der synchrone Write ist an der Quota gescheitert“ wurde „es gibt keinen fremden Schreiber mehr“ geschlossen. Die Quota ist aber eine Eigenschaft des **Ursprungs**, nicht dieses Tabs: sie lässt den ausdrücklichen Save eines anderen Tabs aus demselben Grund auf IndexedDB zurückfallen, also ist gerade auf diesem Pfad ein fremder Save **besonders wahrscheinlich** am Laufen. Die Ausnahme wurde außerdem als „letzte Gelegenheit, also unbedingt schreiben“ gerechtfertigt, obwohl es eine dritte Möglichkeit gibt, die Runde 2 im >5-MB-Zweig selbst schon benutzt: fragen und den Timer stehen lassen.
- **Fix:** Der Zweig ist jetzt symmetrisch zum >5-MB-Zweig — für nicht ausdrückliche Arbeit **kein** `put` (D4). Damit „Bleiben“ nichts verliert, wird der von `cancelPendingSave()` verworfene Timer neu eingeplant: `const standSaveAus = !!saveTimeout` **vor** `cancelPendingSave()` erfassen, im `!explicit`-Zweig dann `saveAutomatic(); _unloadFlushDeclined = true; _askToStay(event);`. Das `saveAutomatic()` ist die treue Wiedereinplanung (der abgelehnte Timer war zwangsläufig rein automatisch, sonst wäre `explicit` wahr), und seine **erneute** Veraltungsprüfung im Timer-Körper schützt dabei Tab B. Das erneute `_unloadFlushDeclined = true` ist nötig, weil `save()` die Markierung löscht — sonst zieht der `pagehide`-Flush den Save doch vor. Ausdrückliche Arbeit wird weiter sofort gerettet: `_hasExplicitPendingWork()` ist auch bei `_lastPersistFailed` und `_persistWritesInFlight > 0` wahr, der Wächter nimmt der Rettung also genau die Fälle nicht weg, in denen wirklich nur eigene Daten auf dem Spiel stehen.
- **Regel:** Ein Fehlschlag, der aus dem **Ursprung** kommt (Quota, Speicherdruck), trifft alle Tabs gleichzeitig — er ist ein Grund, mit einem fremden Schreiber zu rechnen, nicht einer, ihn auszuschließen. — Und eine Rückfrage, die **nach** dem Schreiben kommt, ist keine Entscheidung des Nutzers, sondern eine Benachrichtigung: erst entscheiden lassen, dann schreiben — oder gar nicht schreiben und den Weg offen halten, auf dem nach „Bleiben“ gerettet wird.
- **Bekannte Grenzen:** Verlässt der Nutzer die Seite trotz Rückfrage, verfällt die nicht ausdrückliche Änderung (bewusst, D4/D5). Nach „Bleiben“ rettet der neu eingeplante Timer erst 300 ms später, und seine Veraltungsprüfung verwirft ihn, wenn der andere Tab inzwischen gespeichert hat — dann bleibt das Konflikt-Banner die Meldung. Ausdrückliche Saves bleiben last-writer-wins.

Mutations-Matrix gegen den in-memory mutierten Quelltext, jede Mutation tötet genau die Zusicherung, die sie beschreibt: die Runde-2-Fassung (Notrettung bedingungslos) → `U9h` (harmlose Nebenänderung, zwei Tabs, Quota voll: genau **ein** `put`, „Borin“ überlebt), `U9i` (dasselbe mit ausstehendem automatischem Save, plus `defaultPrevented`), `U29` (ein Tab: **kein** `put` beim Entladen, aber Rückfrage); `saveAutomatic()` weggelassen → `U29b` (Nutzer bleibt, der neu eingeplante Timer rettet nach IndexedDB); `_unloadFlushDeclined = true` weggelassen → `U29`, `U9i` (der `pagehide`-Flush zieht den Save doch vor); `_askToStay(event)` weggelassen → `U29`, `U29b`, `U9i`; `_persistNow(false)` im ausdrücklichen Zweig weggelassen → `U29c` (ein AUSDRÜCKLICHER Save wird beim Entladen weiter sofort gerettet). `U9f`, `U9g` und `U30` bleiben grün und grenzen den Fix ab.

### R06 Nachtrag: Konflikt-Neuladen mischte statt zu ersetzen, degradierter Start galt als sauberes Laden (F3)

- **Problem:** Vier Befunde am Laden und Neuladen.
  **(A)** `load()` übernahm den gespeicherten Stand mit `Object.assign(D, parsed.p)` — auch auf dem Neuladen-Pfad (`reloadData()` → `_loadForReload()` → `load({strictIdb:true})`). Ein Schlüssel, den **nur** das verdrängte `D` dieses Tabs trug, überlebte das Neuladen, und der nächste gewöhnliche `save()` schrieb ihn zurück. Genau die Schlüssel also, die ein „Überschreiben“-Import (`importDataGlobal`, R03) oder ein Backup-Restore (`applyRestoredCampaign`, R01) in einem **anderen** Tab über `replaceCampaignData()` entfernt hatte: das empfohlene „🔄 Neu laden“ machte diese Löschung teilweise zunichte (nachgestellt: importierte Kampagne endet mit dem alten `partyGold`, den alten `randomTables`, `quickRefCustom` und `dmScreenNotes` — **der alte Inhalt**; nach dem Fix ist genau dieser Inhalt fort, `randomTables`/`quickRefCustom` kommen danach aber als **Standard** zurück, siehe „Bekannte Grenzen“). Zusätzlich setzte ein gespeicherter eigener `__proto__`-Schlüssel per `Object.assign` den **Prototyp** von `D`.
  **(B)** Der degradierte Start galt als sauberes Laden. Lag in localStorage eine Kopie **ohne** `_ts` (so hinterlässt es eine Quota-Rettung nach IndexedDB) und scheiterte das IndexedDB-Rohlesen, nahm `load()` den Schatten, meldete `{ok:true, degraded:true}`, zeigte **nichts** an und setzte eine **normale** Baseline. Der Tab galt damit als nicht veraltet: `saveAutomatic()` (Session-Timer, Reparatur nach `load()`, Zufallstabellen-Seed) und der Entlade-Write schrieben den ungeprüften Schatten **mit** `_ts` — und ab dann übersprang jedes spätere `load()` die IndexedDB-Prüfung (`quick-roll.js`: `if (s && !lsTimestamp)`). Der neuere IndexedDB-Datensatz war dauerhaft verdeckt. Der Entlade-Write davon ist eine Verschlechterung aus R02: die Basis vor R02 schrieb beim Entladen kein `_ts`, der nächste gesunde Start fand den IndexedDB-Stand also wieder. Der Schwesterzweig (IndexedDB-Lesefehler bei **leerem** localStorage) macht es seit R06 richtig: keine Baseline, Warnung, automatische Saves gesperrt.
  **(C)** Die Entscheidung, den geladenen Stand neu festzuschreiben, fiel zu früh. `_afterReloadApplied()` verglich `getPersistSuccessCount()`; dieser Zähler steigt erst **nach** dem IndexedDB-Commit. Ein `saveImmediate()` einer > 5 MB großen Kampagne, das im Ladefenster startet (z. B. Strg+Z), legt seine Transaktion **während** des gehaltenen Lesens an und committet nach IndexedDB-Planungsregel erst **danach** — beim Entscheiden stand der Zähler also noch auf dem Startwert, das Neu-Festschreiben fiel aus, und der späte Commit schrieb den **verdrängten** Stand in IndexedDB, während `D` den geladenen trug und die Oberfläche „🔄 Daten neu geladen“ und „gespeichert“ meldete. Schlimmer noch: sein `_onPersistSuccess()` setzte die Baseline mit `external:false` neu und hob damit die Veraltung auf, die für einen im Fenster eingetroffenen **fremden** Save gesetzt worden war — Banner sichtbar, Tab trotzdem nicht veraltet, automatische Saves wieder erlaubt (gegen D4 und gegen die Zusicherung „Banner sichtbar ⇒ veraltet“).
  **(D)** Der Undo-Punkt „Neu laden (anderer Tab)“ hielt den Stand vom **Klick**. Eine Änderung mit `saveUndoState()` im Ladefenster legte denselben Stand auf den Stack; die Dedup-Regel von `_pushUndoSnapshot()` verwarf den Neuladen-Schritt, und die Änderung aus dem Fenster lag danach in **keinem** Schnappschuss.
- **Ursache:** (A) Der gemeinsame Ersetzungspfad (`replaceCampaignData` + `CAMPAIGN_FORBIDDEN_KEYS`) entstand in R01/R03 für Restore, Import und Löschung; `load()` blieb bewusst außen vor, weil der **Start** die lazy angelegten Schlüssel behalten muss. Dass „Start“ und „Neuladen“ zwei verschiedene Aufgaben mit derselben Funktion sind, wurde dabei nicht aufgelöst. (B) Aus „wir können weiterarbeiten“ wurde „wir haben gültig geladen“; `degraded` war ein Feld im Ergebnis, aber kein Zustand im Tab, und niemand liest das Ergebnis (`core/init.js`). (C) Ein Zähler, der Erfolge **zählt**, wurde als Anzeige dafür benutzt, ob ein Save **läuft** — die beiden Zeitpunkte liegen im IndexedDB-Modus eine Transaktion auseinander. Zugleich wurde der fremde Save als Wahrheitswert **vor** dem Warten erfasst statt als Frage **nach** dem Warten. (D) Der Snapshot wurde dort genommen, wo die Absicht entsteht (Klick), nicht dort, wo der Stand verloren geht (Übernehmen).
- **Fix:**
  (A) `load()` kennt die Option `replace`. Ist sie gesetzt, entsteht der neue Stand als `initializeData()` plus die gespeicherten Schlüssel (`CAMPAIGN_FORBIDDEN_KEYS` übersprungen) und wird per `replaceCampaignData(D, next)` übernommen — dieselbe Gestalt, die ein Start erzeugt, ohne verdrängte Reste und ohne je `__proto__` zuzuweisen. `_loadForReload()` setzt `replace: true` neben `strictIdb`; der Startpfad mischt unverändert weiter.
  (B) Im Erfolgspfad von `load()` folgt direkt hinter `setPersistBaseline()`: bei `degraded` einmal `markExternalCampaignWrite(key)` und die Warnung „⚠️ Kampagne konnte nicht aus IndexedDB gelesen werden“. Der Tab ist damit veraltet — keine automatischen Saves, kein Entlade-Write. Ein **ausdrücklicher** Save schreibt weiter (D4) und setzt die Baseline neu.
  (C) `_reloadDataNow()` erfasst `getPersistGeneration()` statt des Erfolgszählers (die Generation steigt **synchron** beim Start jedes Saves) und übergibt den Fremd-Save-Test als **Funktion**. `_afterReloadApplied(beforeJSON, generationAtStart, foreignSaveSinceFn)`: unveränderte Generation → `true`; sonst `await window.waitForPersistSettle()`, **danach** `foreignSaveSinceFn()` prüfen, und nur ohne fremden Save `await saveImmediate()`. Dessen Transaktion wird nach der des Fenster-Writes angelegt, committet also zuletzt. Der `encounterRound`-Nachzug und `(renderAfterDataReplace || renderAll)()` bleiben unverändert.
  (D) `_loadForReload(onBeforeApply)` ruft den Rückruf **innerhalb** von `shouldApply`, nach der Aufgabe-Prüfung und unmittelbar vor dem Übernehmen; `_reloadDataNow()` serialisiert `beforeJSON` dort neu (`try`/`catch`, im Fehlerfall `null`, also wie `pushUndo()` ohne Undo-Punkt weiter). Die Serialisierung beim Klick bleibt als Startwert.
- **Regel:** „Laden“ und „Neuladen“ sind nicht dieselbe Aufgabe: der Start **füllt** auf, das Neuladen **ersetzt**. Wer fremde Daten per Zuweisung in ein bestehendes Objekt übernimmt, muss `__proto__`/`constructor`/`prototype` ausschließen — `JSON.parse` legt `__proto__` als eigene Eigenschaft an, `Object.assign` löst daraus den Prototyp-Setter aus. — Ein eingeschränkter Ladevorgang muss einen **Zustand** im Tab setzen, nicht nur ein Feld im Ergebnis: ein Ergebnis, das niemand liest, schützt nichts. Wer eine ungeprüfte Kopie weiterverwendet, darf sie nicht so zurückschreiben, dass die Prüfung danach entfällt. — Ein Zähler, der **Abschlüsse** zählt, sagt nichts darüber, ob gerade etwas **läuft**. Wer nach einem Rennen entscheiden will, muss auf das Ende warten (`waitForPersistSettle()`) und die Bedingungen **danach** erneut auswerten — ein vor dem Warten erfasster Wahrheitswert ist zum Zeitpunkt der Entscheidung schon alt. — Ein Undo-Punkt wird dort genommen, wo der Stand verloren geht, nicht dort, wo die Absicht entsteht.
- **Bekannte Grenzen:** Der **Startpfad** mischt weiterhin per `Object.assign`, einschließlich der `__proto__`-Empfindlichkeit: ein bereits gespeicherter `__proto__`-Schlüssel wirkt beim Start, nicht mehr beim Neuladen (eigenes Vorhaben — `initializeData()` legt die lazy angelegten Schlüssel wie `randomTables`, `quickRefCustom`, `partyGold` und `dmScreenNotes` nicht an, ein Ersetzen beim Start würde sie also bei jedem Start verwerfen und neu säen lassen). `replace` wirft die Schlüssel des verdrängten Stands **absichtlich** weg: eine Änderung, die dieser Tab an einem Schlüssel gemacht hat, der im gespeicherten Stand fehlt, ist nach dem Neuladen nur noch über Strg+Z erreichbar (Undo-Schritt „Neu laden (anderer Tab)“). Und `replace` ist nicht das letzte Wort über die lazy angelegten Schlüssel: der Frame, den `renderAfterDataReplace()` → `renderAll()` danach einplant, sät zwei von ihnen als **Standard** neu — `initQuickRefCustom()` setzt `D.quickRefCustom = []` bedingungslos, `renderRandomTables()` → `initRandomTables()` legt die **drei Standardtabellen** an und schreibt sie per `saveAutomatic()` auch fest (nach erfolgreichem Neuladen ist der Tab nicht veraltet, der Write geht durch). Eine Kampagne, die ein „Überschreiben“-Import bewusst **ohne** Zufallstabellen gebracht hat, trägt danach also wieder die Standardtabellen. Das ist **kein** Verhalten des Neuladen-Pfads: ein gewöhnlicher Start macht dasselbe, weil `core/init.js` nach `load()` `renderAll()` **und** `window.renderRandomTables()` direkt aufruft. Der verdrängte **Inhalt** kommt dabei nicht zurück, und `partyGold`/`dmScreenNotes` bleiben fort, weil kein Render-Pfad sie anlegt. Ob das Nachsäen direkt nach einem Neuladen überhaupt schreiben soll, ist offen (eigenes Vorhaben — es betrifft den Startpfad gleichermaßen). `waitForPersistSettle()` wartet höchstens `PERSIST_SETTLE_CAP_MS` (5 s); committet ein Write länger, entscheidet das Neuladen wie bisher zu früh. Der degradierte Start zeigt pro Start eine Warnung — in einem Browser mit dauerhaft unbrauchbarem IndexedDB also jedes Mal (bewusst: die Alternative war das stille Verdecken). Die Veraltung nach einem degradierten Start hebt jeder ausdrückliche Save auf, auch wenn IndexedDB noch immer nicht lesbar ist: das ist D4 (last-writer-wins) und keine Prüfung. Die drei übrigen Pfade, die `D` ersetzen (Restore, „Überschreiben“-Import, Undo/Redo), ziehen `encounterRound` weiterhin **nicht** nach (U8 minor:4 breiter gefasst, eigenes Vorhaben); der **Restore** zeichnet seit F4 über `renderAfterDataReplace()`, „Überschreiben“-Import und Undo/Redo zeichnen weiter nur über `renderAll()`; `_afterReloadApplied()` ruft weiterhin kein `refreshPersistSnapshot()` (U8 open:5).

### Nachtrag: `.app-title` war keine Bereitmeldung — Klicks im Startfenster gingen verloren (F8)

- **Problem:** Jede Wartebedingung der E2E-Suite prüfte den Selektor `.app-title` — 42 Stellen in 21 Specs plus `loadApp()` im gemeinsamen Helfer. Die Kopfzeile steht im **statischen HTML** des Bundles (im gebauten Dev-Bundle bei Zeile ~22.074, das große `<script>` beginnt erst bei ~26.987), sie ist also schon beim Parsen da und sagt **nichts** darüber, ob die App bedienbar ist. `core/init.js` wartet auf `await load()` und hängt die Klick-Listener der Navigation (`.nav-tab`) sowie den delegierten `document`-Klick-Handler erst **danach** an; für `.nav-tab[data-view]` gibt es keinen delegierten Ersatzpfad. Ein Klick oder ein Einfügen im Fenster dazwischen wird daher stillschweigend verschluckt: die Ansicht bleibt auf „Start“, eine Einfüge-Operation erreicht den Editor-Handler nicht. Gemessen im Vollauf: `editor-insert.spec.js:507` scheiterte mit leerem Editor (`textContent` `''`), und im 3×-Stresslauf der vier Editor-Specs scheiterte `editor-smoke.spec.js:259`, weil der „+ NPC“-Knopf nicht sichtbar war — der Bildschirmabzug zeigt die Nav-Gruppe offen und die Ansicht weiter auf „Start“. Beide laufen einzeln grün. Das Rennen bestand schon vorher; der asynchronere Start aus U3/U7/U8 hat das Fenster verbreitert.
- **Ursache:** Es gab **keine** maschinenlesbare Aussage „init() ist durch“. Die Tests warteten deshalb auf das Nächstbeste — ein DOM-Element, das mit der Initialisierung nichts zu tun hat — und deckten die Lücke mit `waitForTimeout(500)` ab. Eine Zeitspanne ist keine Bedingung: unter Last (Vollauf mit mehreren Arbeitern) reicht sie manchmal nicht, und wenn sie reicht, weiß niemand, warum.
- **Fix:** `core/init.js` setzt nach **allen** init-Schritten `document.documentElement.dataset.appReady = 'true'` (Attribut `data-app-ready`) und zusätzlich `window.__appReady = true` für Harnesses ohne DOM-Abfrage. Der bisherige Rumpf liegt unverändert in `initSteps()`; `init()` ist die Hülle `try { await initSteps(); } finally { … }`. Das `finally` ist der Kern: wirft ein init-Schritt, ist die App eingeschränkt, aber „so bereit wie sie wird“ — ohne die Markierung würde ein Test 15 s auf einen Zustand warten, der nie mehr kommt. Die Markierung bedeutet also **„init() ist durchgelaufen“**, nicht „alle Schritte haben funktioniert“; der Fehler fliegt wie bisher weiter und wird vom Aufrufer gemeldet. Kein CSS hängt am Attribut, kein Template ändert sich. Auf der Testseite gibt es jetzt **einen** Ort für die Wartebedingung: `waitForAppReady(page)` in `tests/e2e/helpers/test-utils.js` wartet zweistufig — erst `.app-title` (billig, wie bisher), dann `page.waitForFunction` auf die Markierung. Alle 42 Stellen laufen darüber; `loadApp()` ebenso.
- **Regel:** Eine Wartebedingung muss an dem hängen, was der Test braucht, nicht an dem, was zuerst sichtbar ist. Statisches Markup taugt nicht als Bereitmeldung — wer Verhalten testet, wartet auf eine Zusicherung des **Verhaltens**, nicht auf ein Element. Und eine Bereitmeldung, die nur im Gutfall gesetzt wird, ist keine: sie muss auch der gescheiterte Lauf setzen, sonst tauscht man ein Wackeln gegen ein Hängen. Ein `waitForTimeout` neben einer echten Bedingung ist ein Verdachtsmoment, kein Schutz.
- **Bekannte Grenzen:** Die Markierung sagt nichts über den **Erfolg** der init-Schritte; ein Test, der eine bestimmte Initialisierung braucht, muss deren Wirkung selbst prüfen. ### Drei Nutzerentscheidungen vom 2026-09-27: Verdrängungsregel, sicheres Löschen mit Nutzerwahl, verlustfreier Kampagnenwechsel (F9)

- **Problem:** Drei Stellen entschieden über Daten, ohne dass die Entscheidung getroffen war. **(D-A)** Fiel IndexedDB aus **und** meldete localStorage eine volle Quota, durfte die letzte Verdrängungsstufe von `pickLocalBackupEviction()` (`systems/backups.js`) das **neueste — womöglich einzige** Backup einer **fremden** Kampagne wegnehmen, damit das neue Backup der aktiven Kampagne Platz fand (Akzeptanz R05, Szenario S8a). **(D-B)** War `window.indexedDB` gemeldet, ließ sich die Datenbank aber nicht **öffnen** (ältere Firefox-Privatfenster, manche `file://`-Aufbauten), scheiterte „Alle Daten löschen“ und das Löschen der Standard-Kampagne fail-closed mit „Es wurde nichts gelöscht“ — die Kampagne war dort **überhaupt nicht** löschbar. **(D-C)** Wechselte ein **veralteter** Tab mit ausdrücklicher, ungespeicherter Änderung die Kampagne, schrieb `flushPendingSaveAndSettle()` zu Recht nichts, ließ den Save aber eingeplant: das `beforeunload` des Neuladens fragte nach (D5), und nach „Bleiben“ zeigte der Tab die **alte** Kampagne, während `index.active` schon auf die neue zeigte.

(D-B) `removeCampaignData()` meldete jeden IndexedDB-Fehler gleich (`stage: 'indexedDB'`); die Aufrufer konnten „Datenbank nicht öffenbar“ (Kopie **unbekannt**) nicht von „Commit abgebrochen“ (Kopie belegt **erreichbar**) unterscheiden und mussten den strengeren Fall annehmen. (D-C) `switchCampaign()` schrieb den Index und rief `location.reload()`, ohne den Zustand des ausstehenden Saves zu berücksichtigen; die einzige Reaktion darauf war die native Rückfrage, die den Index **nicht** zurücknimmt.
- **Fix:** (D-A) Neue Reihenfolge in `pickLocalBackupEviction()`: (1) verwaiste Einträge (kein `campaignKey` oder Kampagne nicht im Index), (2) **eigene** ältere Einträge — nie die eigene geschützte neueste Sicherungskopie, (3) ältere Einträge fremder Kampagnen, **nur solange dieser Kampagne danach mindestens ein Backup bleibt**. Das letzte verbleibende Backup einer fremden Kampagne weicht nie; darf nichts weichen, liefert die Funktion `-1` und das neue Backup scheitert ehrlich (`'failed'`, kein Erfolgs-Toast) — die Live-Daten der aktiven Kampagne sind ohnehin gespeichert. (D-B) `removeCampaignData()` trägt bei `stage: 'indexedDB'` jetzt `reason: 'open' | 'commit'` (unterschieden an `window.idb`, das nach einem gescheiterten Öffnen leer bleibt). Bei `'open'` fragt der neue Helfer `confirmLocalOnlyCampaignRemoval()` (`systems/spellslots/persistence.js`) per native `confirm()`: Abbrechen (empfohlen, erst exportieren) oder **nur** die localStorage-Kopie löschen, mit benannter Folge („die mögliche IndexedDB-Kopie bleibt und kann beim nächsten Start wieder auftauchen“). Erst die Bestätigung löscht; die Meldung danach sagt, was gelöscht wurde und was nicht. Beide Aufrufstellen (`clearStorage()`, `deleteCampaign()`) gehen darüber. (D-C) `switchCampaign()` ruft `secureStaleTabBeforeSwitch()`: ist der Tab veraltet (`isCampaignStorageStale`) **und** hat er ausdrückliche Arbeit (neu exportiert: `hasExplicitPendingWork()`), wird sein In-Memory-Stand als **geschützte** Sicherungskopie (`kind: 'safety'`) der **alten** Kampagne geschrieben und deren Ergebnis abgewartet. Danach sperrt `retireCampaignWrites()` die Schreibpfade — das hält das `beforeunload` still und verwirft den ausstehenden Save —, dann erst wird der Index geschrieben. Scheitert die Sicherungskopie, wird **nicht** gewechselt.
- **Regel:** Wer Platz für eigene Daten schafft, darf nie die **letzte** Kopie fremder Daten dafür hergeben — ein ehrlich gescheiterter Schreibvorgang ist besser als ein gelungener auf Kosten von etwas Unwiederbringlichem. Und: „aus Sicherheit gar nichts tun“ ist keine Sicherheit, wenn es den Nutzer handlungsunfähig macht — die Alternative ist nicht, still zu entscheiden, sondern **den Nutzer entscheiden zu lassen** und die Folge zu benennen. Ein Zustand, in dem zwei Speicherorte einander widersprechen (`index.active` neu, Anzeige alt), darf nicht als Ergebnis einer Abbruchentscheidung entstehen.
- **Bekannte Grenzen:** (D-A) Bei voller Quota **und** ausgefallenem IndexedDB kann die aktive Kampagne jetzt gar kein localStorage-Backup mehr bekommen, wenn nur noch letzte fremde Kopien und die eigene Sicherungskopie in der Liste stehen — das ist die gewollte Richtung, bedeutet aber „kein neues Backup“ statt „ein neues Backup, eine fremde Geschichte weg“. Verwaiste Einträge dürfen weiter unabhängig von ihrer Anzahl weichen. (D-B) Ein abgebrochener Commit auf einer **geöffneten** Datenbank bleibt fail-closed (`T16d`, `T17b`). Die Unterscheidung hängt an `window.idb`: ein Aufbau, der nach einem gescheiterten Öffnen dennoch ein `window.idb` stehen lässt, würde als `'commit'` gelten und wieder fail-closed bleiben. Auf dem Nur-lokal-Pfad entfernt `deleteCampaign()` die Auto-Backups dieser Kampagne **bewusst nicht** (Abweichung von D2 = A): sie sind der einzige Weg zurück, solange die IndexedDB-Kopie unerreichbar ist — der Alert sagt das. (D-C) Liefert die Sicherungskopie `'skipped-empty'` (kein Inhalt nach der gemeinsamen Definition `hasCampaignContent()`), wird gewechselt und ehrlich gemeldet, dass die Änderung **nicht** gespeichert wurde — eine Sicherungskopie könnte dort nichts zurückholen. Scheitert danach der Indexwrite, hebt `resumeCampaignWrites()` die Sperre auf und holt einen verworfenen Save nach; dieser ausdrückliche Save bleibt last-writer-wins (D4), der Stand liegt aber zusätzlich in der Sicherungskopie. Die Sicherungskopie ist gegen die Rotation geschützt, nicht gegen einen späteren `purgeCampaignBackups()` beim Löschen derselben Kampagne.

### R02: der Tabwechsel zog einen rein automatischen Save vor und überschrieb den laufenden ausdrücklichen Save des anderen Tabs (G1)

- **Problem:** Genau der Fall, den U9f/U9g/U9h/U9i für die Entlade-Sequenz festnageln, stand für den häufigsten Auslöser überhaupt offen: der DM wechselt zum zweiten Tab, um dort weiterzuarbeiten. `flushPendingSave()` (`systems/spellslots/persistence.js`) prüfte Schreibsperre, ausstehenden Timer, Suspend-Tiefe, `_unloadFlushDeclined` und Veraltung — **nicht** aber, ob der ausstehende Save ausschließlich von automatischen Schreibern kommt (`_pendingSaveAutomaticOnly`). Beim Verstecken wurde er deshalb vorgezogen, sein `campaigns`-put NACH dem laufenden ausdrücklichen `saveImmediate()` des anderen Tabs angelegt — und committete danach über ihn hinweg. Gemessen an der Basis mit der Mehr-Tab-Werkbank (`G1a`): Tab B legt „Borin“ an und speichert ausdrücklich, Tab A hat nur einen Session-Timer-Autosave ausstehend und gilt als frisch; nach `A.verstecken()` stehen **2** puts statt einem, und im IndexedDB-Datensatz liegt `["Held 0" … "Held 5"]` — Bs bestätigte Arbeit ist weg. Der Pfad reproduzierte auch an den älteren Ständen `ed16746`, `847c7cd` und `a34ffbd`, war also nicht neu.
- **Ursache:** Der Schutz saß an zwei Stellen: `persistOnUnload()` schreibt für nicht ausdrückliche Arbeit nie, und `flushPendingSave()` lässt einen so abgelehnten Save liegen (`_unloadFlushDeclined`). Diese Marke setzt aber **ausschließlich** `persistOnUnload()`, also erst **nach** `beforeunload`. Der `visibilitychange`-Zuhörer feuert bei **jedem** Tabwechsel und Minimieren ohne `beforeunload` (ebenso ein `pagehide` ohne vorheriges `beforeunload`). Dort war die Marke `false`, und der Flush sah keinen Unterschied zwischen ausdrücklicher und automatischer Arbeit. Die Regel D4 stand also nur für den Entlade-Weg im Code, nicht für den Hintergrund-Weg.
- **Fix:** Eine Zeile mehr in `flushPendingSave()`: `if (_pendingSaveAutomaticOnly && !(opts && opts.force)) return;`. Ein rein automatischer Save wird damit behandelt wie ein veralteter Tab — nicht vorziehen, sondern dem regulären 300-ms-Timer überlassen, der die Veraltung seit F2 erneut prüft und dann von selbst nichts schreibt. `{ force: true }` bleibt ausgenommen: `flushPendingSaveAndSettle()` ruft so auf, die internen Festschreib-Stellen (`switchCampaign()`, Pins `U22`/`U30`) schreiben weiterhin fest, und der ausdrückliche Flush beim Verstecken (`U11`) bleibt unberührt. Alle Aufrufer geprüft: `pagehide` und `visibilitychange` rufen ohne Optionen (neu zurückgestellt), `flushPendingSaveAndSettle()` mit `force` (unverändert), `window.flushPendingSave` hat im Quellbaum keinen weiteren Aufrufer; die zwei Testaufrufe (`idb-transaction-commit.test.js`, `conflict-reload.test.js` `T5g`) benutzen ausdrückliche Saves und bleiben unberührt.
- **Regel:** Zwei Schranken, die denselben Schaden verhindern sollen, müssen an derselben Bedingung hängen — nicht an zwei verschiedenen. Hängt die eine an einer Marke, die nur ein Ereignis setzt, deckt sie nur dieses Ereignis: `_unloadFlushDeclined` schützte den Entlade-Weg, während derselbe Flush über `visibilitychange` viel häufiger und ungeschützt lief. Wer eine Unterscheidung „ausdrücklich vs. automatisch“ einführt, muss sie an **jeder** Stelle treffen, die schreiben kann, nicht nur dort, wo der Befund zuerst auffiel.
- **Bekannte Grenzen:** Ein automatischer Save wird beim Tabwechsel jetzt später geschrieben (beim regulären Timer statt sofort). Verloren geht er dadurch nicht, solange die Seite lebt (`G1b`); schließt der Nutzer den Tab in diesen ≤300 ms, greift der bisherige Weg über `persistOnUnload()` samt Rückfrage (D5, `U9g`). Für **große** Kampagnen heißt das, dass der vorgezogene Flush beim Tabwechsel nur noch ausdrückliche Arbeit früh festschreibt — genau die Zusicherung von `U11`, nicht mehr. Ein Save, der automatisch begann und danach ein ausdrückliches `save()` erhielt, zählt wieder als ausdrücklich und wird vorgezogen (`G1d`).

### R03: die Sättigung klebte dauerhaft am ID-Zähler und band gelöschte Verweise an neue Entitäten um (G2)

- **Problem:** `nextId(type)` (`utils/utilities.js`) las die Sättigung aus der **berechneten** ID ab — und die konnte allein deshalb `ENTITY_ID_MAX` (1e15) sein, weil der _Zähler_ 1e15 war (`counter valid && counter >= floor`). Der Sättigungszweig schrieb danach genau diesen Wert zurück, `validateAndRepairNextId()` repariert nur bei `counter <= maxId` und `recomputeNextIds()` behielt jeden gültigen Datei-Zähler ≥ Untergrenze: der Pin überlebte Laden, Undo/Redo, Import und Restore. Der Typ blieb also dauerhaft im Lücken-Modus, obwohl oberhalb von `max(ID)` 1e15 IDs frei waren. Ende-zu-Ende über den echten Restore/Import-Normalisierer gemessen (`normalizeCampaignData`, Datei `{ npcs: [{id:1},{id:2},{id:5}], quests: [{id:1, giverId:3}], _nextId: { npcs: 1e15 } }`): die nächsten NSC-IDs waren `[3, 4, 6]`, der Zähler blieb 1e15, und `quest.giverId = 3` — ein Hänger auf einen früher gelöschten NSC — zeigte danach auf den **neuen** NSC. Zweiter Weg ohne präparierte Datei: eine fremde Entität mit `id: 1e15` löst die Sättigung echt aus, der Pin wird gespeichert, der Nutzer löscht diese Entität und zwei NSCs — nach dem Neuladen vergab die App genau die gelöschten IDs 2 und 3 (Untergrenze wäre 5 gewesen). Löschen räumt Verweise nicht auf, also binden `quest.giverId`, `npc.relations[].targetId` oder Links still an die neue Entität um.
- **Ursache:** `counter == ENTITY_ID_MAX` ist zweideutig: „der Zähler ist an der Grenze angekommen“ oder „eine fremde Datei behauptet 1e15“. Die Korrektur der dritten Runde (F6) hatte den Zähler bewusst als **dauerhaftes** Signal „gesättigt“ benutzt — ein persistenter Wert als Signal für einen Zustand, der gar nicht persistent ist: Sättigung ist eine Eigenschaft der **Sammlung** (reicht sie an die Obergrenze?) und, innerhalb eines Stapels, des laufenden Münzvorgangs. Der Suchzeiger, der die Stapel-Erinnerung trug, wurde im Normalpfad gelöscht und stand damit als Unterscheidungsmerkmal nicht zur Verfügung.
- **Fix:** Drei Änderungen in `utils/utilities.js`. (1) `SATURATION_CURSOR` heißt `MINT_CURSOR` und wird bei **jedem** Münzen fortgeschrieben (`set(type, id + 1)`) statt im Normalpfad gelöscht. Seine reine Anwesenheit sagt „in diesem Prozess wurde für den Typ schon gemünzt, es kann eine ID unterwegs sein, die noch in keiner Sammlung steht“. (2) Vor dem Sättigungszweig: `if (!isMintableEntityId(id) && isMintableEntityId(floor) && !MINT_CURSOR.has(type)) id = floor;` — ist die berechnete ID nicht vergebbar, die Untergrenze aber schon, dann stammt sie aus dem Zähler und ist genau `ENTITY_ID_MAX` (der einzige gültige, nie vergebbare Wert); ohne Zeiger ist nichts unterwegs, also trägt allein die Sammlung die Wahrheit und die monotone Vergabe setzt ab der Untergrenze wieder auf. Innerhalb eines Stapels bleibt der Zeiger gesetzt und die Lückensuche zuständig — sonst wäre die Untergrenze ein zweites Mal vergeben (das ist der Grund für (1)). (3) `recomputeNextIds()` verlangt für Registertypen `isMintableEntityId(counter)` statt `isValidEntityId(counter)`: ein Datei-Zähler von genau 1e15 trägt keine Vergabe-Information (er wird nie gemünzt) und fällt bei harmloser Sammlung auf die Untergrenze zurück — dort, wo garantiert keine Vergabe unterwegs ist. Der Zähler bekommt in der Sättigung weiter `ENTITY_ID_MAX`, aber nur noch als gültigen Platzhalter (`N12`), nicht mehr als Signal. Gemessen nach dem Fix: neue IDs `[6, 7, 8]`, Zähler 9, `giverId = 3` bleibt ein Hänger; nach dem Löschen der Obergrenzen-Entität und einem Neuladen `[5, 6]` statt `[2, 3]`.

Gemessen am gebauten Bündel (gefüllte Kampagne, 1440 px, echte Tastendrücke): in 400 Sprüngen 34 `BODY`-Halte, 329 Halte auf frisch erzeugten Knoten, 860 entfernte Knoten. Zum Vergleich über drei Ansichten mit derselben globalen Schale und je 20 Zeilen: NSC erreicht die Schnell-Referenz in 37 Anschlägen, die Initiative in 196, das Bestiarium in 220 **nicht**.
- **Ursache:** `render()` ersetzte bei **jedem** `scroll`-Ereignis `visibleContainer.innerHTML` — auch wenn `startIdx`/`endIdx` unverändert blieben. Der eben fokussierte Knoten war danach `isConnected === false`, `document.activeElement` fiel auf `BODY`, und der nächste Tabulator setzte **innerhalb** der frisch gebauten Zeilen wieder auf statt dahinter.
- **Fix:** Zwei Teile in `ui/virtual-scroll.js`. (1) Kein Neuzeichnen bei unverändertem Fenster — das war der häufigste Fokusverlust und zugleich Arbeit ohne Wirkung. (2) Verschiebt sich das Fenster wirklich, wird der **absolute Zeilenindex** plus die Stelle des fokussierten Elements **innerhalb** der Zeile gemerkt (nicht der Knoten — er ist genau das, was verloren geht) und der Fokus an den frischen Knoten derselben Zeile zurückgegeben. Steht die Zeile nicht mehr im Fenster, bleibt es beim Verlust: dann ist der Spielleiter über sie hinausgerollt, und ihm den Fokus nachzuziehen wäre ein Griff in die Bedienung.
- **Zwei Fallen in der Reparatur selbst:** `div.focus()` auf einem `div` **ohne** `tabindex` ist ein Nichts — kein Fehler, keine Wirkung; die Fokussierbarkeit entsteht erst in der Nachrüstung (`ui/keyboard-reach.js`), einen Bildwechsel später. Darum wird `KeyboardGroup.aktualisieren()` in **derselben** Aufgabe angestoßen. Und `focus()` **muss** hier `preventScroll: true` tragen, sonst rollt es sein Ziel in den sichtbaren Bereich, das erzeugt ein `scroll`, das denselben Lauscher erneut weckt — Rückkopplung.
- **Regel (Messdisziplin):** **Eine Messung in Maschinengeschwindigkeit unterschätzt diesen Fehler.** Mit 0 ms Pause zwischen den Tastendrücken waren 17 Stellen unerreichbar, ab 30 ms deterministisch 27; Menschentempo liegt bei 250–600 ms, der Spielleiter trifft also immer den schlechten Fall. Wer Tastaturwege prüft, misst mit Pause. Und: wer in einer Liste `innerHTML` ersetzt, verliert den Fokus — die Reparatur gehört an die Ursache (das Neuzeichnen), nicht in die Tastaturmechanik.
- **Datei:** `ui/virtual-scroll.js`
- **Tests:** `tests/e2e/features/tastatur-reichweite.spec.js`

### Fokusrückgabe ohne `preventScroll` ließ die Liste zurückspringen

- **Problem:** Im Bestiarium: Fokus auf der ersten Monsterzeile, 300 px mit dem Rad gerollt — danach stand `scrollTop` wieder auf 0 statt auf 300. Die Liste sprang unter der Hand des Spielleiters zurück und machte genau die Bewegung zunichte, aus der das Neuzeichnen entstanden war.
- **Ursache:** `_holeFokusZurueck()` rief `ziel.focus()` ohne `preventScroll`. Der Standardwert rollt das Ziel in den sichtbaren Bereich — eine **Fokusrückgabe ist aber keine Navigation** und darf die Ansicht nicht bewegen.
- **Warum im Kampfpaket unsichtbar:** `renderInit()` rollt nichts, und `.init-spell-slots` liegt in keinem rollbaren Behälter. Der Fehler entstand nicht mit den Vorbereitungsansichten, er wurde dort nur erstmals sichtbar.
- **Fix:** `ziel.focus({ preventScroll: true })` in `_holeFokusZurueck()`. Der Gegensatz dazu steht bewusst daneben: in `_tasten()` **ist** die Bewegung gewollt, weil der Spielleiter selbst fährt und sein Ziel sehen will. Darum steht `preventScroll` an der einen Stelle und nicht an der anderen.
- **Regel:** `focus()` zur Wiederherstellung immer mit `preventScroll: true`; `focus()` als Folge einer Benutzerfahrt ohne. Wer beides gleich behandelt, hat entweder einen Sprung oder ein unsichtbares Ziel.

### `aria-expanded` folgte dem Zustand nicht (Auftragsköpfe)

- **Problem:** Ein Klick auf einen Auftragskopf klappte die Karte auf, `aria-expanded` blieb aber auf `"false"`. Das Vorleseprogramm hörte „eingeklappt", während der Auftrag offen stand. Gemessen mit je einem echten Klick und 1,5 s Nachbeobachtung: `toggle-quest` „false" → „false" bei offener Karte (falsch), `toggle-shop` „false" → „true" (richtig). **Genau eine** der vier Aufklapp-Familien war betroffen, nicht drei — die beiden Einzelstellen (`toggle-collapse`, `toggle-wiki-category`) tragen gar kein `aria-expanded`.
- **Ursache:** `toggleQuest()` in `features/quests/quests-render.js` schaltet **nur eine Klasse** um (`element?.classList.toggle('expanded')`) — keine `childList`-Änderung, kein `save()`. Der `MutationObserver` von `KeyboardGroup` horchte ausdrücklich nur auf `childList`, der Post-Save-Haken feuerte nicht, die Regelfunktion lief nie.
- **Gegen den Ausgangsstand war das eine Verschlechterung:** vorher trug der Kopf gar kein `aria-expanded`, das Hilfsmittel schwieg. Eine Falschaussage ist schlechter als Schweigen.
- **Fix:** Am allgemeinen Ort, nicht in `toggleQuest()`: der Beobachter horcht zusätzlich auf `attributeFilter: ['class']`. In `toggleQuest()` wäre es eine Zusicherung an einer von vier Familien gewesen, und die nächste Funktion, die nur eine Klasse umschaltet, wäre wieder stumm. Dass der Beobachter sich damit nicht selbst weckt, ist nachgemessen: **im Code** von `ui/keyboard-group.js` kommt weder `classList` noch `className` vor. Der naheliegende Beleg reproduziert dabei NICHT — `grep -nE "classList|className" ui/keyboard-group.js` liefert **zwei** Zeilen, und zwar zwei Kommentare, von denen der eine genau diesen Befehl zitiert. Es ist dieselbe Selbstfalle, die diese Akte für ihre Zahlangaben schon kennt (Zahlen in Worten, damit `DOC-12` nicht auf der Fehlerbeschreibung selbst anschlägt). Reproduzierbar ist der Beleg erst ohne die Kommentarzeilen: `grep -nE "classList|className" ui/keyboard-group.js | grep -vE "^[0-9]+: *(//|\*)"` ist leer.
- **Regel:** **Ein Zustandswechsel, der nur eine Klasse umschaltet, ist für einen `childList`-Beobachter unsichtbar.** Wer ARIA aus einer Klasse ableitet, muss auf `attributeFilter: ['class']` horchen. Zweite Lehre, aus dem Nebenbefund: `toggleCollapse()` in `systems/spellslots/navigation.js` entging demselben Fehler nur **beiläufig**, weil es sein Pfeil-Icon per `textContent` umschreibt und damit zufällig eine `childList`-Änderung erzeugt. Eine Abhängigkeit von einem Icon ist keine Zusicherung.
- **Dritte Lehre, über den Wächter:** die vorhandenen Fälle lasen den Zustand **einmal**, direkt nach dem Öffnen der Ansicht, und prüften eine Anzahl gegen ein Soll. Damit belegen sie die **Anwesenheit** des Attributs, nie seine **Richtigkeit** — ein tautologischer Wächter. Ein Fall über ein Zustandsattribut muss **zuerst bedienen und danach lesen**, und vorher prüfen, dass die Bedienung den Zustand überhaupt geändert hat.
- **Datei:** `ui/keyboard-group.js`
- **Tests:** `tests/e2e/features/tastatur-gruppen.spec.js` (18g, 18g-T)

### Die Tastenhilfe gab den Fokus frei, statt ihn ihrem Öffner zurückzugeben

- **Problem:** Nach dem Nachziehen der Tastenhilfe (Fokus fällt beim Öffnen in den Dialog) lag der Fokus beim Schließen mit Escape auf `BODY` statt auf dem geklickten ⌨️-Knopf. Nachgewiesen von der **vollen** Playwright-Suite, von genau dem Fall, der dafür gebaut ist: `tastatur-ausloesung.spec.js` (g2) klickt den Knopf, drückt Escape und sichert zu, dass der geklickte Knopf den Fokus **behält** — „ohne diese Zusicherung misst der Fall nichts".
- **Ursache:** Eine halb richtige Begründung. Ein Öffner wurde absichtlich nicht gemerkt, weil ein **vorgetäuschter** Öffner die Leertaste verbraucht (derselbe Fehler, den `tastatur-kuerzel.spec.js` (j) für den HP-Rechner festhält). Richtig ist nur die Hälfte davon: einen Öffner **erfinden** ist falsch, einen vorhandenen **wiederherstellen** ist richtig — und `ui/modal-focus.js` tut für die 36 Schalen genau Letzteres.
- **Fix:** Beim Öffnen wird das fokussierte Bedienelement gemerkt, **sofern es eines gibt**. Bei `?` liegt der Fokus auf `BODY`, der Öffner ist `null`, und der Fokus wird beim Schließen freigegeben — die Leertaste gehört wieder dem Zugwechsel. Beim Klick auf den ⌨️-Knopf gibt es einen, und er bekommt den Fokus zurück. Keine `WeakMap` nötig: es gibt eine Tastenhilfe, sie schachtelt nicht, und `showShortcutsOverlay()` ist ihr einziger Öffner im Baum.
- **Regel:** Eine Fokusübergabe in einen Dialog braucht **immer** den Rückweg, und zwei Zusicherungen aus **zwei Richtungen**: eine, dass der Fokus hineingeht, eine, dass er zurückkommt. Eine Umsetzung, die nur eines kann, ist dann in genau einem der beiden Fälle rot. Und: eine Teilsuite hätte diesen Regress nicht gefunden — er lag in einer anderen Datei als die Änderung.

- **Problem:** Die Hilfe druckt die Zeile „Nächstes Bedienelement (im Dialog bleibt er darin)". Gemessen am gebauten Bündel (1440x900, echte Tastendrücke) verließen **44 von 45** Tabulatorsprüngen die **offene** Hilfe, 35 davon landeten auf einem Ziel, das die Blende verdeckt (`document.elementFromPoint` über der Mitte liefert `DIV.shortcuts-overlay`), während die Hilfe sichtbar offen blieb. ### Für ein Vorleseprogramm war die ganze Tastenhilfe ein Textknoten

- **Problem:** Der Zugänglichkeitsbaum der offenen Hilfe bestand aus **drei** Knoten: ein Text, ein Knopf, und ein rund hundert Wörter langer Satz für vierzig Zeilen — ohne Trennung zwischen Handlung und Taste und ohne Überschrift, nach der man springen könnte. `#shortcuts-overlay` und `.shortcuts-modal` trugen `role`, `aria-label`, `aria-labelledby` und `aria-modal` je auf `null`; im Dialog null Überschriften, null Rollen, null `aria-*`-Attribute, null `<kbd>`, null Listen.

- **Fix:** Die Fußzeile klebt (`position: sticky`) am Fuß des Laufbereichs und nennt alle drei Wege samt dem Hinweis, dass die Liste weitergeht; der ✕-Knopf ist 44 px unter 601 px und 32 px darüber. Das Log tritt beiseite, solange die Hilfe offen ist — über eine Marke am `<body>`, **nicht** über die Ebenenleiter: eine Ausnahme für eine Blende hätte die Leiter entwertet. Der Preis steht im Kommentar: ein Hinweis, der währenddessen abläuft, ist danach weg; dafür gibt es die dauerhafte Betriebsart des Logs, und die steht in der Hilfe.
- **Regel:** Eine modale Fläche, die länger ist als ihr Platz, braucht ihren Ausweg **sichtbar** — und zwar den Ausweg des Geräts, nicht den der Tastatur. Und: eine gezählte Ebenenleiter ist nicht der Ort, an dem man einen Überdeckungsfehler repariert; die obere Schicht tritt beiseite.

### Ein `min-width: 0` auf der Tastenreihe machte aus einem lauten Fehler einen stillen

- **Problem:** Beim Umbau der Hilfe zur Beschreibungsliste bekamen `<dt>` **und** `<dd>` ein `min-width: 0`. Isoliert nachgemessen bei 601 px (Spalte 237,4 px), mit einer langen Beschriftung auf einer **dreigliedrigen** Marke: `min-width` auf beiden → Querlauf 9 px, keine dreizeilige Zeile; `min-width` nur auf `dt` → Querlauf 0, die Zeile dreizeilig. Der Ausgangsstand hatte an allen gemessenen Breiten Querlauf 0.
- **Ursache:** Auf der Definition erlaubt `min-width: 0` der **Tastenreihe**, unter ihren Inhalt zu schrumpfen; die Marken hängen dann rechts aus dem Dialog. Ein Querlauf **in** einem Dialog ist auf dem Telefon praktisch unauffindbar — und kein Fall sah ihn: der zuständige Fall fuhr nur 390, 360 und 1440 px, und dort tritt er nicht auf. Die Begründung für das `min-width` war außerdem falsch: das früher dort stehende `<span>` war ebenso ein Flex-Kind mit `min-width: auto` und brach korrekt um.
- **Fix:** `min-width: 0` nur auf dem Begriff. Eine zu lange Beschriftung bricht dann auf drei Zeilen um, und **das** meldet der Fall laut. Der Fall fährt seit diesem Befund auch 601, 700 und 1440 px, mit der Spaltenbreite je Stufe als eigener Zusicherung.
- **Regel:** Zwischen zwei Fehlerbildern ist das **auffällige** zu wählen. Ein Fehler, der einen Wächter auslöst, ist dem vorzuziehen, der sich versteckt — und eine Zusicherung, die nur an drei Breiten fährt, deckt kein Band. Zweite Lehre: eine Breitenangabe in einem Kommentar („zwei Spalten von 267 px für 601-900 px") ist eine Zusicherung ohne Wächter; gemessen sind es bei 601 px 237,4 px.
- **Dateien:** `assets/styles/dmscreen.css`, `tests/e2e/features/tastenhilfe.spec.js`
- **Tests:** `tests/e2e/features/tastenhilfe.spec.js` (8)
